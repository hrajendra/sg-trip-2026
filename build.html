How it unfolded
Phase 1 — Trip planning (no app yet)
It started with flights. "Help me plan a family trip to Singapore." Visa requirements, hotel shortlisting, day-by-day itinerary — the app didn't exist yet. The key insight that shaped everything: different members needed the same trip communicated completely differently.
Phase 2 — First app, one page
"Can you turn this itinerary into a mobile web app?" One HTML file, tabbed day view. Functional but basic — no audience separation, no food details, no dietary tags.
Phase 3 — Multi-page architecture
"The grandparents need their own simpler guide — one in English, one in Telugu." This expanded the app to four pages. The grandparent pages became progressively simpler: fewer slots, larger text, no logistics they didn't need.
Phase 4 — PWA and installability
"Can this be installed as an app on their phones?" First attempt had a subtle bug: start_url: "/" pointed to the GitHub Pages root, not the app's subdirectory, so installs silently failed. Fixed to "./index.html".
Phase 5 — Food as a feature
Dish lists with dietary tags (🌿 🍗 👶 🍼 ⭐), stall numbers, sugar flags for the toddler. Then dishes.js — a single data file powering all three pages so updating one venue updates everywhere.
Phase 6 — Polish
Countdown timer, shortened hero, Places and Food split into separate tabs, custom hibiscus icon generated in Python, hotel updated across 14 references in one pass, nav bugs tracked down to orphaned closing divs.
Retrospective
✓ What worked well
Plain English is enough. "The nav is broken — clicking Day 2 does nothing" produced a fix faster than any Stack Overflow search. Describing problems in human terms was more useful than technical descriptions.
✓ What worked well
Small changes, deploy often. Testing each change in the browser before requesting the next kept the app stable. When three things changed at once and something broke, it was harder to isolate.
✓ What worked well
No framework was the right call. Pure HTML/CSS/JS meant last-minute itinerary edits could be made directly on GitHub from a phone — no local setup, no build step.
△ Do differently next time
Start with dishes.js from day one. Dish lists were copy-pasted into each HTML file individually before the shared data architecture arrived. Starting centralised saves several rounds of syncing.
△ Do differently next time
Run div balance checks from the start. The most frustrating bugs were unbalanced HTML divs — a missing </div> causing an entire day's content to bleed across all tabs. Became standard practice by phase 5, should have been from phase 1.
△ Do differently next time
Establish "nothing private in the app" on day one. Confirmation numbers started appearing in app code before someone caught that the repo is public. Set the rule early.
△ Do differently next time
One consistent HTML structure across all pages. The three guides ended up with slightly different attribute patterns (data-day vs data-t). A shared base structure defined upfront would have kept cross-page changes simpler.
Build your own
1️⃣
Get a free account at claude.ai and a free account at github.com. That's all you need.
2️⃣
Paste your trip details and itinerary into Claude. Be specific about your group — who they are, what languages they speak, any dietary needs.
3️⃣
Ask for a mobile PWA with separate views per audience. Tell Claude: "No framework, no build step, pure HTML/CSS/JS — I need to edit files directly on GitHub."
4️⃣
Upload the files to a new GitHub repo and enable GitHub Pages (Settings → Pages → main branch). Live in 60 seconds.
5️⃣
Iterate. Test in your browser, describe what's wrong or what you want to add, get new code. Repeat.
